# 플로우 구성 설계 결정 (초안)

플로우 빌더·실행 UX를 구현하기 전에 합의한 규칙을 기록한다.

## 1. 플로우의 역할

- 플로우는 **여러 시나리오를 이어 붙인 뒤 그대로 실행할 수 있는 단위**다.
- 조합(캔버스/표)만이 아니라 **실행**이 1급 시민이다.

## 2. 저장 후 수정

- 플로우가 **한 번 저장되면 당분간 수정은 허용하지 않는다.**
- 편집은 러너·경로 선택 등이 안정된 **다음 단계**에서 연다.

## 3. 경우의 수(경로)

- **한 줄기(선형 순서)** 를 기본 단위로 생각한다.
- 표의 한 행 = 사용자가 선택·실행할 수 있는 **하나의 시나리오 순서**에 대응할 수 있다.

## 4. 시나리오를 이을 때 — 후보 목록

**결정: 다음에 붙일 시나리오를 고를 때, 이전 시나리오의 “마지막 URL”과 다음 시나리오의 “첫 URL”이 일치하는 것만 보여주지 않는다.**

| 이유 | 설명 |
|------|------|
| 데이터 신뢰 | 마지막 스텝 URL은 SPA·리다이렉트 등으로 **안정적으로 뽑기 어렵다.** |
| 예측 가능성 | 매칭 성공/실패·후보 0건 등에 따라 목록이 바뀌면 **같은 화면인데 규칙이 달라 보여** 사용자가 헷갈린다. |
| 단순 규칙 | **정확하지 않은 휴리스틱은 쓰지 않는다.** 상황별로 다른 값을 주지 않는다. |

**대안(현재 방향):** 이어 붙이기·플로우 구성 시 시나리오 후보는 **항상 동일한 규칙으로 전체 시나리오**를 제시한다. (검색·정렬·그룹 필터 등은 UX 보조일 뿐, “URL 매칭으로 자동 축소”는 하지 않는다.)

> 참고: 검사 중인 탭과 **호스트만** 맞추는 필터(예: 도메인 스코프)가 있다면, 그것은 “URL 체인 매칭”과 별개의 옵션으로 둔다. 체인 매칭으로 목록을 좁히는 기능은 도입하지 않는다.

## 5. 이후 검토 가능 항목

- 시나리오에 **명시적 “끝 URL”** 등 신뢰 가능한 신호가 생기면, 그때 별도 스펙으로 “추천만 표시” 같은 보조 UX를 논의할 수 있다. (필수 필터로 쓰지 않는 전제 유지 권장.)
